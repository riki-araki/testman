# ラボ01: 別のネットワークにいるサーバーへ届かない

## 構成

```
 ┌──────────┐   lan_a 10.101.1.0/24   ┌──────────┐   lan_b 10.101.2.0/24   ┌──────────┐
 │  client  │─────────────────────────│  router  │─────────────────────────│  server  │
 │ .1.10    │                  .1.254 │          │ .2.254                  │ .2.10    │
 └──────────┘                         └──────────┘                         └──────────┘
                                                                              nginx :80
```

- `client` と `server` は **別のネットワーク (サブネット)** にいます
- 両者は `router` を経由しないと通信できません
- 各コンテナのデフォルトルートは削除してあります（インターネットに出られない「プライベートサブネット」）

## ミッション

1. `lab start 01` で起動し、まず **正常な状態** を観察する
   - `lab shell 01 client` で入り、`curl http://10.101.2.10` が成功することを確認
   - `ip route`, `ip addr`, `traceroute -n 10.101.2.10` の出力をメモしておく
2. `lab break 01` で障害を起こす
3. 「client から server の Web ページが見えない」という報告を受けた想定で、原因を調査して直す
4. `lab check 01` で合格すれば完了。`lab break 01` を繰り返して **4 種類すべての障害** を直してみましょう

## 学べること

- IP アドレス・サブネット・ルーティングテーブルの読み方
- ルーターが「パケットを転送する」とはどういうことか (`ip_forward`, `FORWARD` チェーン)
- 「行き」だけでなく **「戻り」の経路** も必要であること
- 調査の基本手順: `ping` → `traceroute` → `ip route` → `tcpdump`

## 使えるコマンド

| コマンド | 用途 |
|---|---|
| `ip addr` / `ip -br a` | インターフェースと IP アドレスを確認 |
| `ip route` / `ip route get <IP>` | ルーティングテーブル / 特定宛先の経路を確認 |
| `ip link` | インターフェースの UP/DOWN を確認 |
| `ping` / `traceroute -n` | 疎通と経路を確認 |
| `tcpdump -ni any icmp` | パケットが実際に届いているか確認 (**最強の武器**) |
| `iptables -S` / `iptables -L -v -n` | ファイアウォールのルールを確認 |

## AWS との対応

| このラボ | AWS |
|---|---|
| lan_a / lan_b | サブネット |
| `ip route` | ルートテーブル |
| router | (VPC 内の暗黙のルーター) / Transit Gateway / NAT インスタンス |
| router の `iptables FORWARD` | Network ACL |
| デフォルトルートなし | プライベートサブネット (IGW へのルートなし) |

AWS では「ルートテーブルにルートがない」「戻りの NACL で塞がれている」などが典型的な疎通トラブルです。
このラボで身につけた **「行きと戻りを 1 ホップずつ確認する」** 考え方はそのまま使えます。
