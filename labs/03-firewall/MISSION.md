# ラボ03: iptables で必要な通信だけを通す

**タイプ: 構築 (build)** — ここまでのラボと違い、最初は「何も守られていない」状態から始まります。

## 構成

```
  client (10.103.0.20) ──┐                ┌─────────────────────────────┐
                         ├── dmz ────────▶│ web (10.103.0.10)            │
  admin  (10.103.0.30) ──┘                │   :80   公開サイト            │
                                          │   :8080 管理画面 (機密)       │
                                          │  ┌───────────────────────┐   │
                                          │  │ fw (iptables を操作)   │   │ ← 同じネットワーク名前空間
                                          │  └───────────────────────┘   │
                                          └─────────────────────────────┘
```

## ミッション

### Part 1: 構築

1. `lab start 03` で起動し、`lab check 03` を実行。**管理画面が誰にでも見えてしまう** ことを確認する
   - `lab shell 03 client` → `curl http://10.103.0.10:8080` で機密情報が見えてしまう
   - `nmap -Pn 10.103.0.10` で攻撃者目線でどう見えるか確認
2. `.runtime/03-firewall/firewall/rules.sh` の TODO を埋める (ホスト側のエディタで編集できます)
3. `lab shell 03 fw` → `sh /firewall/rules.sh` で適用
4. `lab check 03` で 8/8 合格すれば構築完了
5. 完成した `rules.sh` は `journal/` などに保存しておきましょう (**`lab reset` / `lab stop` で消えます**)

### Part 2: 障害対応

6. `lab break 03` で「誰かが入れた変なルール」を発生させる
7. `iptables -L INPUT -v -n --line-numbers` でルールを読み、原因を特定して直す
   - パケットカウンタ (`pkts` 列) が増えているルールを見ると、どのルールにマッチしているか分かります
8. 4 種類すべて直してみましょう

## 学べること

- iptables のチェーン・ポリシー・ルールの評価順序 (**上から順に、最初にマッチしたもので決まる**)
- ホワイトリスト方式 (デフォルト拒否) の考え方
- ステートフルファイアウォール (`conntrack`) と戻りの通信
- `DROP` と `REJECT` の違い、攻撃者 (nmap) からどう見えるか
- Kubernetes の Pod と同じ「ネットワーク名前空間の共有」(`network_mode: service:web`)

## AWS との対応

| このラボ | AWS |
|---|---|
| rules.sh (INPUT チェーン) | セキュリティグループのインバウンドルール |
| デフォルトポリシー DROP | SG は「許可ルールのみ」で、それ以外は暗黙的に拒否 |
| `conntrack ESTABLISHED` | SG は **ステートフル** なので戻りは自動で許可 |
| `-s 10.103.0.30` | ソースに特定 IP / 別の SG を指定 |
| シナリオ 3 のミス | 管理ポートを `0.0.0.0/0` に開けてしまう (**現実の侵害原因の定番**) |

AWS の SG は「上から順に評価」ではなく「どれか 1 つでも許可なら許可」です。この違いも意識しましょう。
