# ラボの作り方

ラボを自分で作ることは、ラボを解くよりも深い学習になります。
「どう壊れるか」「どうすれば壊れたと判定できるか」を考えるには、仕組みを正確に理解している必要があるからです。

## 手順

```sh
cp -R labs/_template labs/04-dns
cd labs/04-dns
```

1. `lab.conf` にタイトル・難易度・タイプを書く
2. `compose.yml` で環境を作る
   - サブネットはラボ番号から決める (ラボ 04 なら `10.104.x.0/24`)
   - 調査用コンテナには `nicolaka/netshoot` を使う
   - ホストにポートを公開するなら `127.0.0.1:` を付ける
   - 学習者に編集させたい設定ファイルは `files/` に置き、`${LAB_RUNTIME}/...` をマウントする
3. `verify.sh` を書く — **正常な状態で合格することを確認**
4. `break.sh` を書く — **各シナリオで不合格になることを確認**
5. `MISSION.md`, `HINTS.md`, `SOLUTION.md` を書く
6. `make lint && tests/e2e.sh 04` でテストする
7. `README.md` のラボ一覧と `docs/ROADMAP.md` を更新する

## 良いラボの条件

- **症状から始まる**: 「DNS の設定を直せ」ではなく「サイトが開けないという問い合わせが来た」
- **正常状態を観察できる**: 壊す前に、正しい状態を見て理解できる
- **シナリオが複数ある**: 同じ症状でも原因が違うと、切り分けの練習になる
- **verify は「あるべき状態」を検証する**: 「特定の直し方をしたか」ではなく「正しく動いているか」を判定する。別の正しい直し方も合格にする
- **一見正常な障害を混ぜる**: エラーは出ないが冗長性が失われている、セキュリティホールが空いている、など
- **AWS との対応を書く**: ローカルで学んだことがクラウドでどう活きるか

## 使える関数 (lib/common.sh)

| 関数 | 用途 |
|---|---|
| `dc <args>` | このラボに対する `docker compose` |
| `dx <service> <cmd...>` | コンテナ内でコマンドを実行 |
| `pick_scenario <最大> [指定]` | シナリオ番号を選ぶ (指定がなければランダム) |
| `expect_ok "説明" <cmd...>` | コマンドが成功すれば合格 |
| `expect_fail "説明" <cmd...>` | コマンドが失敗すれば合格 |
| `verify_summary` | 結果を表示し、全項目合格なら 0 を返す |

break.sh / verify.sh には次の環境変数が渡されます:
`LAB_ROOT`, `LAB_ID`, `LAB_DIR`, `LAB_PROJECT`, `LAB_RUNTIME`

## タイプ

| タイプ | 始まり方 | 合格の記録 |
|---|---|---|
| `break-fix` | 正常な状態で起動 → `lab break` で壊す | 壊した後に `lab check` に合格 |
| `build` | 未完成の状態で起動 → 学習者が構築する | 初めて `lab check` に合格 |

`build` タイプのラボでは、自動テストのために `solution/apply.sh` (解答を適用するスクリプト) を用意してください。
