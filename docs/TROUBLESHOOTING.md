# 障害調査の「型」

障害対応で最も大事なのは、**当てずっぽうで設定を変えない** ことです。
観測 → 仮説 → 検証 を繰り返し、原因の範囲を半分ずつ狭めていきます。

## 基本の流れ

1. **症状を正確に言葉にする**
   - × 「つながらない」
   - ○ 「client から server:80 への HTTP が 3 秒でタイムアウトする。ping も通らない」
2. **正常時との差分を探す** — だから `lab start` の直後に正常状態を観察しておくことが大事
3. **下の層から順に確かめる** (または、真ん中から二分探索する)
4. **1 回に 1 つだけ変更する**。変えたら確かめる。効かなければ元に戻す
5. **直ったら「なぜ直ったか」を説明できるか** 確かめる。説明できなければまだ終わっていない

## 層ごとのチェックリスト

| 層 | 確認すること | コマンド |
|---|---|---|
| L1/L2 リンク | インターフェースは UP か | `ip -br link` |
| L3 アドレス | 正しい IP が付いているか | `ip -br addr` |
| L3 経路 | 宛先への経路はあるか、戻りの経路はあるか | `ip route`, `ip route get <IP>` |
| L3 疎通 | どこまで届くか | `ping`, `traceroute -n`, `mtr -n` |
| L4 ポート | ポートは開いているか、誰が待ち受けているか | `ss -tlnp`, `nc -zv <IP> <port>`, `nmap` |
| FW | 通信を落としているルールはないか | `iptables -L -v -n --line-numbers` (カウンタに注目) |
| 名前解決 | 名前が正しい IP に解決されるか | `dig <name>`, `getent hosts <name>`, `/etc/resolv.conf` |
| L7 アプリ | ステータスコードは何か、ログに何が出ているか | `curl -v`, `docker logs`, `/var/log/...` |
| 設定 | 文法は正しいか、反映されているか | `nginx -t`, 設定の再読み込み |

## 最強の道具: tcpdump

「パケットが来ているか、来ていないか」が分かれば、問題の場所は半分に絞れます。

```sh
tcpdump -ni any icmp                 # ping だけ
tcpdump -ni any 'tcp port 80'        # HTTP だけ
tcpdump -ni eth0 host 10.101.1.10    # 特定ホストとの通信だけ
tcpdump -ni any -w /tmp/cap.pcap     # 保存して Wireshark で開く
```

- SYN が来ているのに SYN-ACK を返していない → 待ち受けていない / FW で落としている
- SYN-ACK を返しているのに相手に届かない → 戻りの経路の問題
- 何も来ていない → 手前 (送信元・経路・FW) の問題

## HTTP ステータスコードの読み方 (プロキシ構成の場合)

| コード | 意味 | よくある原因 |
|---|---|---|
| 404 | そのパスはない | location / ルーティングの設定ミス |
| 502 Bad Gateway | プロキシはバックエンドから正しい応答を得られなかった | バックエンド停止、ポート違い、プロトコル違い |
| 503 Service Unavailable | 使えるバックエンドがない | 全台ヘルスチェック失敗、メンテナンス |
| 504 Gateway Timeout | バックエンドが時間内に応答しなかった | バックエンドが遅い、FW で DROP されている |

## 調べ方のメモを残す

調査中に打ったコマンドと結果をメモしておくと、振り返り (`journal/`) がそのまま書けます。
`script` コマンドでターミナルの操作を丸ごと記録することもできます。
